# テスト駆動開発（TDD）規約

本テンプレートはテスト駆動開発を前提にする。このドキュメントを読めば、
新規参加者がテストを書き始められる状態を目指す。

## 1. 基本サイクル

1. **Red** — 失敗するテストを先に書く。仕様を「振る舞い」として表現する
2. **Green** — テストを通す最小限の実装を書く
3. **Refactor** — テストが緑のまま構造を整える

## 2. 層ごとの適用方針

TDD が有効に働く層とそうでない層を分ける。全てに機械的には適用しない。

| 層 | 適用 | テスト手段 |
|---|:--:|---|
| Rust: ドメインロジック・純粋関数（`crates/core/src/domain/`） | 必須 | ユニットテスト（`#[cfg(test)]`） |
| Rust: DB アクセス（`crates/core/src/db/`） | 必須 | インメモリ SQLite に対する統合テスト |
| Rust: コマンド層（`src-tauri/src/commands/`） | 推奨 | モックアプリ経由で入出力を検証（`tauri::test`） |
| Rust: OS 連携（トレイ・通知・FS） | 対象外 | 薄いラッパーに留め、手動確認とする |
| フロント: hooks・ストア・変換ロジック | 必須 | Vitest |
| フロント: コンポーネント | 推奨 | Testing Library（振る舞い単位。スナップショットは使わない） |
| フロント: 画面全体の結線 | 対象外 | E2E で担保する（`e2e/`、TDD サイクルの外） |

## 3. テスト可能性を担保する設計制約

- **コマンドを薄く保つ** — `#[tauri::command]` は入力の変換・検証とロジック関数の呼び出しだけを行う。ロジックは `crates/core`（tauri に依存しない別クレート）に置き、それ単体でテストする
- **副作用を境界に寄せる** — ファイル I/O・HTTP・時刻取得はトレイト越しに扱い、テストでは差し替える
- **DB 接続は引数で受け取る** — グローバル状態から取得しない。テストごとに独立した接続を渡せるようにする
- **フロントは生成された bindings を直接呼ばない** — `src/lib/api/` で一段ラップし、テストではその層を差し替える。IPC そのもののモックが必要な場合のみ `@tauri-apps/api/mocks` を使う

## 4. テストの配置

```
crates/core/src/**/*.rs   # unit test は同ファイル内 #[cfg(test)] mod tests
crates/core/tests/        # DB を含む統合テスト（インメモリ SQLite）
src-tauri/tests/          # コマンド層の統合テスト（モックアプリ経由）
src/**/*.test.ts(x)       # コンポーネント・hooks は対象ファイルの隣に配置
src/test/                 # テストセットアップ・IPC モック・ファクトリ
e2e/                      # WebDriver ベースの E2E（TDD サイクル外）
```

## 5. 命名規約

テスト名から「何が保証されているか」が読めることを優先する。

- Rust: `fn returns_error_when_input_is_empty()` のように、状況→結果を関数名で表す
- TS (Vitest): `it("returns an error toast when the command rejects", ...)` のように文で書く
- 実装の内部構造（関数名・変数名）ではなく、外から見た振る舞いを検証する

## 6. 回転速度の担保

1 サイクルの待ち時間が長いと TDD は破綻する。

- フロントのユニットテストはウォッチモード（`pnpm test:watch`）で即時に再実行される
- Rust のテストは `cargo watch -x 'test -p app-core'` 等で自動再実行できる。`crates/core` は tauri に依存しないためビルドが軽い
- **アプリの起動を伴うテストはサイクルに入れない** — E2E とネイティブ機能の確認は PR 前・CI 側に置く

## 7. CI との関係

- PR チェックではユニット・統合テストを全て実行する
- E2E は別ワークフローとし、TDD の速度を犠牲にしない
- **CI は「テストが落ちたこと」だけを理由にブロックする。「テストが無いこと」ではブロックしない** — 誤検知のコストが高いため。テストの不在は手元の Hooks（`docs/automation.md`）とレビュー観点（`docs/review-checklist.md` §5）で捕まえる

## 8. テストデータの規約（QA-13）

- 固定値をテストごとにベタ書きせず、`src/test/factories/` （フロント）・`crates/core/tests/support/` （Rust）にファクトリ関数を置く
- ファクトリは「テストに必要な最小限のデフォルト値」を返し、個々のテストは差分だけ上書きする
- テスト間で DB やファイルなどの状態を共有しない。インメモリ SQLite は 1 テストにつき 1 接続を作る
